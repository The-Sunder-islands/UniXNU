## 2. 第一次上电尝试（H227/H228，`sheng-gpu-power=1`）

每 beat 只做一步，避免日志爆发被吞：

| 步 | 动作 | 实测 |
| --- | --- | --- |
| 1 | 解除 GX clamp（0x0130=0） | `clamp now=00000000` ✓ |
| 2 | CX GDSC（0x1004 bit0=0 + 轮询） | `cx=18222000 collapsed=0` ✓ |
| 3 | gfx3d_clk_src ← XO（0x1074=0，0x1070 清 bit31 + UPDATE） | `gfx3d_rcg=80000000` ✗ bit31 清不掉 |
| 4 | gfx3d 分支使能（0x1098 bit0 + bit13） | `gfx3d_branch=80002621 running=0` ✗ |
| 5 | GX GDSC（0x1094 bit0=0 + 轮询） | `gx=08222000 collapsed=0` ✓ |
| 6 | GX reset 脉冲 + 读 RBBM | RBBM 三字全 0（`gc=24/25/26 = 00000000`） |

## 3. 判读与下一步

- GDSC 的 `SW_COLLAPSE` 已清 → 控制器层面接受"上电"；
- 但 `gfx3d` 根/分支的 bit31 保持 1、RBBM 全 0（不是挂死）→ 域未真正授压/授时；
- 三个待补齐点（C1c）：
  1. **VOTABLE GDSC 的 vote**：`gpu_cx_gdsc`/`gpu_gx_gdsc` 为主线 `gdsc.c` 的 votable
     类型，除清 `SW_COLLAPSE` 外还要写 `gds_hw_ctrl`(0x1008) 的 vote 位；
  2. **根时钟语义**：确认 `CMD_RCGR` bit31 是 ROOT_OFF 还是只读状态，以及
     gfx3d_clk_src 父时钟（gpupll0 输出 / XO 分支）是否真正产生；
  3. **RPM 的 CX/GX 电压投票**：本端口无 RPM 驱动，最可能是"显示上电但时钟不跑"的根因。

## 4. 日志抓取经验（硬件无响应时尤其重要）

1. 晚探针（~35 s）早于日志 ring 起点（~40 s）→ 打在那里拉不到；
2. 一次 24 行会被写入器快照整批丢弃（H223）；
3. 缓慢分散也会被 371 s 的窗口重置吞掉中段（H224）；
4. **把值放进心跳行并带序号**（H226 `gc=<index>:<value>`）是唯一稳定方式；
5. H221 的整段 GPUCC 扫描在 `0x007c` 之后总线挂死 → 只用定点偏移。

## 5. H229：按 gdsc.c 判定电源状态（2026-11-08）

```text
step2  cx gdscr 00222001->a0282000 status[1008]=80001fe0 on=1   ← CX 成功
step5  gx gdscr 00222001->08282000 status[1094]=08282000 on=0   ← GX 失败
```

- `PWR_ON = BIT(31)`：CX 的 `gds_hw_ctrl`(0x1008) 已置位，说明 GDSC 写入序列正确；
- GX 的 `gdscr`(0x1094) 仍未置位 → GX 轨缺少 RPM 投票（本端口无 RPM 驱动）；
- 因此 `gfx3d` 根时钟不跑、RBBM 读回 0 都源于 GX 未上电，而不是时钟编程错误。

### C1d-3 的候选

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| A | 在 boot_args 内存映射中保留 `0x86000000`+2 MiB，再看 SMEM 是否恢复 | 中（改 loader/ADT 侧的内存映射） |

## 9. C1e-2：SPMI 传输与 PM8005 S1（H236）

SMEM/RPM 在 B 线上不可用（§7、§8），GX 轨只能从 **PM8005 S1** 直写。H235 的
`core+0x0 = 0x30000000` 判定仲裁器是 v3；v3 与 v2 共用 PPID 映射、`0x8000` 通道页和
CMD 格式，因此实现按 v2 数据通路。

### 9.1 传输公式

```text
PPID       = (sid << 8) | (addr >> 8)        5, 0x1400 -> 0x514
通道页     = 0x8000 * apid                   EE 0
CMD        = (opcode << 27) | ((addr & 0xff) << 4) | (bc - 1)
             14 = write, 15 = read
read       = obsrvr + 页 + {CMD 0x00, STATUS 0x08, RDATA0 0x18}
write      = chnls  + 页 + {WDATA0 0x10, CMD 0x00, STATUS 0x08}
STATUS     = DONE bit0, FAILURE bit1, DENIED bit2, DROPPED bit3
APID map   = core + 0x800 + 4*apid, PPID [19:8]
owner      = cnfg + 0x700 + 4*apid, [2:0] == EE 0 才可写
```

代码中没有写 CONFIG（0x04）：厂商驱动同样只在 WDATA0 放数据、再写 CMD，读走 obsrvr。
每次事务最多等 2000 次 STATUS 轮询，失败时把状态留在 `gSpmiLastStatus`。

### 9.2 PM8005 S1 寄存器

```text
基址 0x1400（SID 5）   qcom,qpnp-regulator 公共布局
0x1401 rev   0x1404 type=0x03   0x1405 subtype=0x08/0x09
0x1440 range 0x1441 vset        0x1445 mode(bit7 HPM)
0x1446 enable(bit7)             0x1461 step_ctrl
uV = 375000 + 12500 * vset       (range 0)
```

板级 `regulator-min-microvolt = <524000>`，所以目标取 **525000 µV = range 0 / vset 12**。
`PM8005 S1 + S4` 是两相 VDD_GFX，本轮只开 S1。

### 9.3 三种运行模式与安全闸门

`sheng-gpu-power=2` 只读；`=3` 追加“ENABLE 原值写回 + 读回”；`=4` 追加
RANGE/VSET=525 mV → MODE HPM → ENABLE → GX GDSC → gfx3d 根/分支 → RBBM。

写 PMIC 前同时要求：

1. 8 个 S1 寄存器全部读成功；
2. APID 的 owner == EE 0；
3. TYPE==0x03 且 SUBTYPE∈{0x08,0x09}；
4. GX GDSCR 仍处于 collapse（bit0=1）。

任一不满足即停止，并在 `gc` 留下 `0xdea000xx`。

若读到 `enable` 的 bit7 已为 1 且当前电压在 500–1100 mV 内，第 3 步**不降压**，保持
引导器留下的电压（`gc=97:600d0002`），只补 MODE/ENABLE 并继续重试 GX；只有断电状态
或电压越界时才写 525 mV。

### 9.4 结果通道

`gc=80..111`，顺序与 STATUS H236 的索引表一致，优先于 GPUCC 的 24 个读数输出。
关键判读：`80=30000000`、`81=00000514`、`83=00000000`、`87=00000003`、
`88=00000008`；`104` 的 bit31 才是 GX PWR_ON。

### 9.5 第一轮建议顺序

1. `sheng-gpu-power=2`：确认 APID/owner 与 8 个寄存器，尤其 `enable`/`vset` 当前值；
2. `sheng-gpu-power=3`：确认写通路 STATUS 无 FAILURE/DENIED；
3. `sheng-gpu-power=4`：设 525 mV（或保持已上电电压）并重试 GX。

如果第 1 步就显示 `enable` bit7=1 且电压正常，第 3 步会自动保留该电压，不会把在用的
VDD_GFX 拉低。

若 S1 读回已使能、电压正常，但 `gc=104` 的 bit31 仍为 0（GX 不 PWR_ON），下一候选是同一
两相组的 **S4（外设基址 0x1d00，同一套公共寄存器布局）**：先只读确认它的 range/vset/enable，
再按 S1 的方式补使能。不要在没有读数的情况下直接写 S4。

## 11. H236 实测：SPMI 读通路与 S1 身份（2026-11-08）

`sheng-gpu-power=2` 只读轮成功：

```text
gc=80 30000000  gc=81 00000514  gc=82 00000001  gc=83 00000000
gc=86 00000000  gc=87 0000001c  gc=88 0000000a
gc=89 000000f0  gc=90 00000002  gc=91 00000006
gc=92 00000000  gc=93 00000081  gc=94 ffffffff
```

- APID=1、owner=0：`PPID 0x514` 的映射与 EE 仲裁成立，8 个读事务全部 `rc=0`；
- **S1 是 FTS426**：type 0x1c / subtype 0x0a（FTSMPS2），使用 common2 布局：
  `0x40/0x41` = 16 位小端电压（mV），`MODE 0x45` = 3 位（6=AUTO, 7=HPM）。
  当前 `0x02f0` = **752 mV**，MODE=6，ENABLE=0（轨未开），STEP=0x81；
- 之前的 8 位 RANGE/VSET 解码（375 mV + 12.5 mV×vset）只适用于 GP_CTL buck，
  对本片给出 `range=0xf0` 非法值；`gc=94:ffffffff` 正是这个预期的判据。

代码已按类型分支：`pm8005Voltage()` 对 0x1c 读 16 位 mV，MODE 写 7(HPM)，
电压在 500–1100 mV 内则保留 752 mV，只补 MODE/ENABLE。

另有构建问题：干净重建的补丁循环漏掉了 `zzz-root-auth-bypass.patch`，导致
`native-skip-root-auth=1` 不生效、`bsd_init.c:1103` 提前 panic。补回该 patch 后
H236b（kernel `1d452686…`）出现 `NATIVE_ROOT_AUTH_BYPASS: autherr=80`，日志正常
落盘。后续需要在构建机补丁循环中检查为什么该 patch 没应用，避免再次回归。

下一步：`=3` 同值写验证 → `=4` 保留 752 mV + MODE HPM + ENABLE + GX GDSC。
